Matchmaking and end-to-end networking

What is established about Dragon Ball: The Breakers networking, what the current private server implements, and what must happen before the result can be called compatible with the real client.

Last updated: 2026-11-08 · PR #6

Current position

The managed server now has synthetic implementations of transport, CSMS, matchmaking, connection rooms, P2P relay, and battle lifecycle state. All 68 managed tests pass, and the Release build has zero warnings. This is a strong research baseline, not a live-client success.

No patched native client has completed the full flow against this branch, and no long multi-peer soak has been run. Native validation remains the main outstanding milestone.

2. End-to-end flow at a glance

HTTP bootstrap/auth→ Matching handout→ Encrypted UDP→ CSMS queue→ 8-player battle room→ Connection handout→ Connection room→ P2P + relay→ Results + requeue

HTTPS provides identity, configuration, session handouts, and battle APIs. Custom Diarkis UDP then carries matchmaking and session-room traffic. Bulk gameplay state primarily moves directly between peers, with selected messages relayed through the session host.

3. HTTP bootstrap and authentication

  • The client obtains environment and API base URLs, then authenticates and receives a rolling session token.
  • The captured API route is /dbtb-prd/{prefix}/{title}/api. The server also retains the shorter development route.
  • MessagePack is used for HTTP bodies even where the observed content type appears form-oriented.
  • Battle and queue APIs need to share per-user state rather than return unrelated global placeholders.

4. Matching-server handout and key ownership

battle/get_diarkis_matching_server_info issues a fresh key set for each UDP session. The managed server stores these in a shared registry so HTTP and both UDP listeners resolve the same session.

5. UDP transport and crypto

Datagram header and types

Each datagram starts with a 3-byte little-endian sequence and a 1-byte type.

TypeRoleReliability
1Unreliable dataNo ACK or retransmission
2SYNOpens a session using a 16-byte SID
3Reliable DATACKed; carries command envelopes
4ACKServer ACKs are bare 4 bytes; clients can batch 20-byte records
5RetransmissionRepeats an unacked DAT every 0.5 seconds
6EACKReserved; not observed
7FINTeardown; response ACK uses the answerer's next DAT sequence

Command envelope

  • Magic: FE BE DE EF.
  • Version: one byte; payload size: big-endian 24-bit; command: big-endian 16-bit.
  • Client header: 10 bytes. Server header: 11 bytes with a status byte.
  • Status 01 is success, 04 is an observed error, and FF is a push.
  • Large messages use FF FE FD FC fragmentation, with different client and server wrapping.

Secure envelope

  • Client payloads begin with the 16-byte cleartext SID; server payloads do not.
  • The envelope then contains a big-endian plaintext length, 32-byte HMAC-SHA256 over ciphertext only, and AES-CBC ciphertext.
  • Padding is zero-filled and always adds 1–16 bytes, including a full block when aligned.
  • The IV is fixed per session, not generated per packet.
  • HMAC validation comes before accepting plaintext. A zero declared length can hide meaningful content, and some senders under-report the length.

Bootstrap and maintenance

  1. Client sends SYN; server returns ACK sequence zero.
  2. Client init carries public and LAN addresses; server responds with its observed public address.
  3. NAT and endpoint exchanges use commands 0x0131, 0x012F, and 0x0130.
  4. Heartbeat command 0x0001 echoes the counter and observed address roughly every five seconds.
  5. The cleartext 0c0c directory protocol is separate from RUDP and is not encrypted.

6. CSMS: the game-specific matchmaking layer

DBTB uses custom CSMS messages over commands 12000 and 22000. The public Diarkis ticket sequence is not a substitute.

  • The common header is 54 bytes with an 18-digit string UID.
  • Client requests include title_cd, platform, user_id, id, and data.
  • user_id is a string. Request IDs use CD; response/push IDs use D2.
  • data is a JSON string; fields such as sdpData, roomData, and userData are themselves JSON strings.
  • Responses use request sub-ID + 1000. Pushes add a big-endian total-length prefix.

7. Connection-room handoff

  1. The client requests connection-server information over HTTPS.
  2. It opens the handed-out UDP session using the fresh SID and key set.
  3. Depending on the handout, it may use a redirect probe, move directly to the real listener, or connect without redirect.
  4. Connection-room requests use command 22000 with the same CSMS framing as matchmaking.

8. P2P mesh and relay

Mesh setup

  • Command 127 distributes an opaque mesh blob followed by one record per player.
  • Each record contains the player ID and a base64 blob of length-prefixed public/LAN endpoint strings.
  • Command 301 reports a completed P2P connection. Its plaintext is empty; the observed zero block is padding.

Server-relayed traffic

  • Commands 19 and 24 carry player-state records. Relayed forms are 25 bytes.
  • Command 104 (RoomMessage) handles property synchronization and the in-match message channel.
  • The session host treats game payloads as opaque and relays only to validated members and recipients.
  • Reliable relay messages are retransmitted until ACKed; unreliable messages are not.

Direct peer traffic

Most gameplay state does not pass through the managed server. Direct P2P uses cleartext UDP with the 0b0e0e0d and 0d0e0a0f magic families, a 24-bit little-endian sequence, and a type byte. Setup, keepalive, reliable game data, acknowledgement, and player-state records have been identified. The server mainly needs mesh and relay compatibility, not a game-state serializer.

9. What remains unknown or unproven

Native interoperability

The patched real client has not completed login → queue → match → results → requeue against this branch. Synthetic success must not be represented as a live-client success.

  • Field-level parser callbacks: constructor/callback analysis is still needed for full response and notification behavior. Vtable entries 1/2 return 13000 and 12105; entry-3 functions are deleting destructors, not parsers.
  • Long-run stability: repeated matches, disconnects, and requeues have not been soak-tested.
  • Command 12116: one observed occurrence; meaning remains open.
  • Property-bag details: the first push's extra head/tail and some game-internal record semantics remain unresolved.
  • Some native values: command 101's leading integer and P2P type 5's precise semantics are still inferred.
  • Security and deployment: local placeholder authentication is not suitable for a public server, and native broadcast behavior requires an external firewall during testing.

These unknowns are deliberately separate from the confirmed wire formats. In particular, the opaque game-state internals do not block the current relay implementation unless the real client demonstrates a dependency.

10. Next steps

  1. Run an isolated native-client validation. Use a disposable guest, dedicated account, loopback service/news URLs, and an external firewall allowlist. Capture traffic before launch.
  2. Compare the complete live sequence with the evidence. Check login, queue, match assembly, connection handoff, P2P, results, and requeue. Record failures by route, command, sub-ID, and frame.
  3. Fix one evidenced incompatibility at a time. Add a focused regression test and commit the fix with a short research-log update.
  4. Finish targeted parser research as needed. Use constructors and callbacks to answer concrete client failures rather than broadly decompiling unrelated code.
  5. Run a multi-peer soak. Repeat matches and requeues while checking stale players, fragment growth, unacked state, retransmission, and non-member isolation.
